# Signal Hub 重要信息后台推送设计

状态：用户已批准。日期：2026 年 10 月 2 日。

本功能让用户在关闭网站后，仍能在 Windows Chrome 和 iPhone 上收到系统通知。用户要求只提醒非常重要的信息，不设条数限制，并优先推送“异动”中的重要信号。实现以已有行情规则和可信新闻筛选结果为依据，通过合并重复事件减少打扰；不会为了凑数量发送通知。

## 已确认的要求和本次建议

| 项目 | 规则 |
| --- | --- |
| 通知位置 | 系统桌面或手机通知中心，由后台推送唤起 |
| 优先级 | 重要异动先发送，重要新闻随后发送 |
| 条数和全局间隔 | 不设每日、每小时条数上限，也不设所有事件之间的强制间隔 |
| 降低打扰 | 同一事件去重、合并重复来源，仅在出现新的实质变化时再次提醒 |
| 历史消息 | 首次启用、重新启用和服务重启均不批量补发历史信息 |
| 开关 | 每台设备独立启用、测试和关闭，关闭一台设备不影响其他设备 |

用户已确认设备、重要性、取消数量限制和异动优先，并已审阅批准下面的筛选阈值、新闻来源范围、过期时间和退出登录后的处理。

## 两端使用方式

Windows Chrome 用户在 HTTPS 网站登录后，主动点击“开启通知”并允许浏览器通知权限。关闭网站标签页后，推送不依赖页面继续运行；Chrome 进程仍须在运行。彻底退出 Chrome、电脑关机、网络中断和系统关闭通知时，不承诺即时送达。[Google 技术说明](https://web.dev/articles/push-notifications-faq)

iPhone 需要 iOS 16.4 或更新版本。用户可以在 Chrome 分享菜单中“添加到主屏幕”，再从主屏幕图标打开网站并启用通知。普通 iPhone Chrome 标签页不作为后台通知的启用入口。已有 `src/app/manifest.ts` 和 `src/app/layout.tsx` 提供 standalone 模式、图标和 Apple Web App 元数据。[Google 操作说明](https://support.google.com/chrome/answer/9658361?co=GENIE.Platform%3DiOS&hl=zh-Hans)、[Apple 支持说明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

## 方案选择和推送范围

推荐使用标准 Web Push，沿用 VPS 的持续采集、SQLite 数据和现有主屏幕应用配置。服务器保存设备订阅，并由独立后台进程发送通知。浏览器 Service Worker 负责显示通知和处理点击，不缓存私有页面或 API 内容。

第一版优先复用已经筛选过的异动，并为每日投资简报补上更严格的重大新闻标记和来源时间记录。另一种方案是逐条重新评估 Telegram 和 X，再核验消息中的新闻来源；它覆盖更多原始消息，但会增加外部请求、AI 调用和误判边界，因此留到需要扩大消息范围时再设计。专用桌面及手机应用需要另行安装和维护，也不作为这次网站功能的实现方式。

这里调整了此前“先接 Telegram 和 X 新消息”的建议：原始 TG/X 消息不会自动触发通知，仍在网站里正常更新。已有 `daily-investment-brief.ts` 的重要性分级仅针对 Reuters、AP 等独立新闻候选，不可拿来证明任意 TG/X 消息可靠，也不改变其独立来源边界。

## 什么异动值得通知

异动判断使用行情规则产生的结构化数据。AI 解释、排行榜名次、出现次数、历史回顾、单次 WS 瞬时变化都不能独立决定是否发送。

第一版支持两类重要异动：

1. **行情结构确认。** 候选决策为“关注做多”或“关注做空”，`score >= MARKET_OPPORTUNITY_RULES.actionableScore`（当前为 80），`confidence >= 80`，`mandatoryComplete` 为真，`hardInvalidated` 和 `metrics.stale` 为假。`observedAt` 与对应 enrichment 的 `fetchedAt` 必须合法、不在未来，并在当前 `enrichmentFreshMs` 内（当前为 2 分钟）；`expiresAt` 尚未到期。不能仅因候选 `selected`、进入观察名单或得分较高而发送。“等待确认”“禁止追单”不发送方向性确认提醒。
2. **高等级轧空加速。** 使用现有 `scoreShortSqueeze` 的结果，只接受其规则确认的 level 3“轧空加速”，并要求原始必需行情字段完整、新鲜，事件仍有效。level 1“轧空蓄势”和 level 2“轧空启动”保留在网站展示。推送不把轧空预警表述成已经发生的事实。

所有候选均从完整的已持久化规则结果读取，不从页面前几名、前几条或分页截断的快照读取。现有行情富集本身有候选范围限制，本功能不扩展采集范围，也不能识别从未被采集和评分的市场。现有候选选择数量和页面展示规则不改；这些展示上限不构成推送条数上限。普通大幅波动若没有上述规则确认，不仅凭其 level 自动发通知。

推送系统为每个 `(symbol, direction)` 维护独立的持久 episode：起始确认事件、参与模型、确认阶段最高值和结束依据。机会名单的 `enteredAt`、排名和 `selected` 不作为 episode 身份。同方向 raw squeeze 和机会确认使用共同 episode，但保留各自模型和证据；不会把不同方向合并。

阶段只有“结构确认”和更高的“轧空加速”。首次确认发送一次；同一 episode 达到更高阶段可以再次发送一次，评分细微变化不算升级。五秒内同时到来的确认与加速只发送合并后的最高阶段。同一方向 episode 的所有参与模型都由完整、新鲜的行情明确失效后才结束：机会模型要求连续三个完整扫描不再满足确认，或出现规则的明确 hardInvalidated；轧空模型要求原采集器以有效行情确认 recovery。缺失扫描、过期 enrichment、排名退出、断线和 AI 失败均不能积累结束次数。结束后的下一次新确认创建新 episode。有效的反向确认属于独立方向事件，可以单独提醒。

首次评估已经存在的确认只建立基线。通知启用后的实质升级属于新变化，可以发送。数据过期、采集失败和断线不等于事件已经结束；去重状态须跨进程重启保留。

## 什么新闻值得通知

新闻须同时满足 `importance === "high"` 和新增的 `pushAssessment.exceptional === true`，不能仅凭原有 high 标签就通知。`pushAssessment.category` 只接受“已公布的重大政策决定”“系统性市场或基础设施风险”“已证实的重大安全事故”“关键公司的重大正式公告”；还须给出来自候选素材的简短事实、为什么具有重大影响以及实际候选引用。一般评论、预测、小幅例行更新和证据不充分的候选返回 exceptional 为假。评估在现有简报请求中生成，不新增逐条消息 AI 请求。模型判断仍有误判可能，引用验证证明来源归属，不等于机械证明全部事实和重要性。

服务端只接受实际匹配到可信新闻候选的引用，保留其 sourceId、规范化 URL、来源和时间依据。旧缓存没有 assessment 或来源记录时不推送，不拿模型自报 URL、candidateIndexes 的跨批次编号或非空文案代替来源证据。沿用现有独立候选采集的来源约束，并对 hostname 做精确域名或合法子域名匹配。

新闻首次启用时建立现有条目基线。之后只有新增的、仍满足上述严格评估的来源事件进入低优先级队列。建议只接受可信发布时间在过去 12 小时内、且简报生成时间未超过 12 小时的内容；队列等待超过 1 小时后丢弃，不在下一天补发。

当前 `DailyBriefItem` 没有持久来源时间，必须在候选核验及缓存提交时补上来源映射。RSS 等提供合法 pubDate 时标记为发布依据；GDELT seendate 仅是发现时间，不能当成真实发布时间；解析失败回退到当前时间也不能用于新鲜度判断。没有可信发布时间的新闻保留在简报展示，但不自动推送。不为补齐这些字段而抓取任意候选 URL。

用规范化原始来源 URL 集合建立身份，并以共享引用合并事件；相同的规范化标题作为额外去重依据。每日简报改写标题、调整排序或再次出现同一引用，不重新通知。第一版不对已经关联的新闻事件自动发送后续更新。完全不同的来源引用和标题可能仍指向同一现实事件，因此跨来源语义去重只能尽力完成，不能保证完全消除重复。AI 生成失败时，不退回关键词触发或原始消息全量推送。

## 事件记录和发送流程

重要异动必须在本地规则结果提交时写入同库的持久事件记录。推荐在 `market-alerts-store.ts` 中追加独立 push episode 和 outbox 表。机会候选更新与其 episode 转换和 outbox 写入在同一事务中提交；轧空则把本地有效行情决策、push episode 和 outbox 放入一次本地事务，放在 Telegram 网络发送之前。已有 Telegram 投递的成功、失败或不确定状态不能替代推送决策提交，也不能令同一决策重复入队。

outbox 记录规则版本、episode、事件阶段、发生时间、过期时间、币种、方向、证据和安全站内目标。轧空生产者额外保留全部 `scoreShortSqueeze` 输入（包括当前记录缺失的 `breakout20`）以及行情观测和抓取时间，按同一规则函数确认来源资格。生产者持续保存最新完整轧空评估及明确 recovery 状态；发送器从该本地记录重新校验，不为了发送通知发起新的行情请求。只有完整、两分钟内的新评估仍支持加速，才允许发送。独立推送进程不修改现有行情判断和 Telegram 发送状态。

采用 outbox 而非仅对当前候选快照进行轮询，是因为候选状态会被覆盖，短暂存在的重要确认可能在两次轮询之间消失。附加记录只写本地 SQLite；推送网络请求在数据库事务之外执行。队列消费与本地游标提交应有事务保证，处理时间戳相同的多条事件也不能遗漏。

新闻 assessment、核验过的来源映射及对应 outbox 与简报缓存一起在原有新闻数据库事务中提交，避免缓存覆盖造成漏读。推送进程只消费记录，不额外触发简报生成，也不添加新的 AI 调用或凭据。建议进程每 5 秒扫描异动 outbox，每 60 秒读取新闻 outbox。

发送并发建议为四个槽位，其中三个为异动保留，一个为新闻保留。每轮先领取异动，再领取新闻；同类任务按创建时间先后处理。新闻不会占用异动保留能力，也不会因持续异动到达永远无法开始发送。有限并发和服务商限流仍可能令任务到期；“不设条数限制”表示全部合格事件均持久入队，不表示能保证每一条都在过期前被操作系统展示。

每个设备与事件阶段建立唯一投递记录，状态为 pending、sending、sent、retry、expired 或 dead。领取发送任务需要可恢复的租约，避免多个进程重复消费。发送前再次验证当前规则与行情新鲜度；确认失效后，尚未发送的方向性提醒直接过期。异动推送建议最迟在确认后 2 分钟内投递，超过窗口不补发。进程重启仍恢复尚新鲜的既有 pending/retry 任务；首次启用与重新启用只建立基线，既不补发旧事件，也不清除其他设备的任务。每次启用记录设备 enrollment epoch 和开始时间：忽略此前创建的 outbox，记录当时已有 episode 的最高阶段；新闻还要求可信发布时间不早于这次启用时间。重新启用不会恢复该设备上一次启用时的未完成任务。

不同重要事件不会因每日或每小时计数而被丢弃，也不会被固定一小时间隔阻塞。最多约 5 秒的同事件归并用于等待本轮来源和证据，并不阻塞其他事件。异动与新闻队列分别保留状态；Google 或 Apple 推送服务返回限流时，仅按其响应退避重试。

## 设备订阅和安全边界

新增 `web-push.sqlite` 保存订阅、事件去重和投递状态，使用 `getRuntimeDataPath` 保存在现有持久运行目录。当前应用是单管理员空间，每台设备拥有独立的随机设备标识和取消凭证，不扩展成多用户账户系统。API 不返回其他设备的 endpoint、加密密钥或取消凭证。

新增 `/api/push/config`、`/api/push/subscriptions` 和 `/api/push/test` 等受登录保护的端点。订阅创建、删除和测试都校验管理员会话及同源请求；限制请求体大小并验证订阅密钥形状。注册次数和测试按钮的滥用保护仅约束控制接口，不是重要事件的通知条数上限。

endpoint 是客户端提供的服务器出站目标，必须为 HTTPS、无账户口令、无片段、无异常端口。第一版服务域名白名单为精确的 `fcm.googleapis.com` 和 `web.push.apple.com`，不接受包含这些字符串的其他域名或任意子域名。发送器不跟随重定向，未知服务域名拒绝订阅；如果实际浏览器返回新域名，需要核实提供商后更新白名单。VAPID 公钥提供给浏览器，私钥只存在服务器环境中，不进入源代码、浏览器或日志。

后台发送不依赖浏览器登录 Cookie 持续有效。建议退出登录时取消当前设备订阅；Cookie 自然到期时，订阅继续工作直至用户关闭、推送服务报告失效或管理员撤销。该区别在通知设置说明中清楚呈现。设备关闭通知时先撤销服务器投递资格，再解除浏览器订阅；界面只有在服务器撤销确认后才显示关闭成功。

## 浏览器界面和通知点击

设置页新增“重要信息通知”分类，显示当前设备的权限、订阅状态和服务器是否配置完成，提供“开启通知”“发送测试通知”“关闭通知”。不在进入网站时自动索要权限。iPhone 普通标签页显示添加到主屏幕的操作指引；权限被拒绝或环境不支持时给出可执行的说明。

新增根作用域 Service Worker，仅处理 push 和 notificationclick。通知包含事件标题、简短事实及重要原因；不显示设备标识、服务器错误或密钥。默认内容可以出现在锁屏上，设置中需明确告知。异动使用站内 `/alerts` 目标并可带币种或事件引用，新闻指向对应简报位置。点击只允许本站目标：优先唤醒已有窗口，否则打开新窗口；没有登录时由现有登录代理处理回跳。

采用稳定 notification tag 缓解同一事件重复占据通知中心的问题，真实升级沿用该事件的 tag 更新通知。它只能缓解服务器已被推送服务接收但未完成本地记账时的重复发送；不能承诺跨网络“恰好一次”。sent 表示推送服务已接收，不代表操作系统已经显示或用户已经看到。

## 部署和故障处理

新增独立 `web-push-worker.mjs`，按现有 VPS systemd 模式运行，补齐健康状态。VAPID 私钥、公钥、合法联系 subject 和启用开关通过环境提供，密钥跨发布版本保留。未配置时健康状态显示未启用，网站和其他采集继续工作；配置无效时禁止推送并给出不含秘密的错误状态。

部署脚本的 service 和 script 数组一起更新。回滚到没有该脚本的旧 release 时，应先停用新服务并恢复旧版服务列表，不能因缺失文件导致回滚持续失败。订阅数据库和 outbox 均存放在版本之外的持久运行目录，保留去重记录，不能因重新部署清空。

404 或 410 使订阅失效并停止投递；超时、429 和临时 5xx 在有效窗口内退避重试，到期即停止。连续的配置或认证错误显示在系统健康页。生产启用前需检查站点 HTTPS、服务器到 Google 和 Apple 推送服务的网络连通性，并完成两个真实设备的测试；这些外部条件目前尚未验证。

## 验收标准

- Windows 关闭网站标签页后仍收到一条真实测试通知；点击能打开对应网站位置。
- iPhone 从 Chrome 添加到主屏幕后开启通知，关闭网站时仍能收到真实测试通知。
- 等待确认、缺字段、过期、禁止追单、原始 WS 高频变化及普通新闻不推送。
- 首次确认发送一次；相同异动 episode 或共享来源 URL 的重复、刷新增译、AI 文案、排行榜变化及服务重启不重复发送，真实阶段升级可以发送。不同原创新闻的语义重复单独评估，不宣称完全去除。
- 当出现大量不同的重要事件时，全部进入队列，异动先处理；不因每日或每小时计数而丢弃。对因有效窗口或提供商故障未能投递的任务准确记录过期原因。
- 首次安装、重新启用、断线恢复和新版本发布不补发已存在或过期的旧消息。
- 对订阅越权、跨源修改、恶意 endpoint、提供商失效及重试租约恢复进行行为测试。
- 数据写入和 outbox 在同一事务中提交；突发事件及相同时间戳不丢失，机会列表的页面数量限制不会截断通知源。
- 完成相关单元与集成测试、项目要求的 lint 和构建，再分别进行 Windows 与 iPhone 实机后台收通知验收。模拟测试不能替代真实推送和系统通知显示验收。

本设计仅形成可审阅方案，尚未写入产品代码、配置生产凭据或部署。
